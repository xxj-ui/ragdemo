## 3. 实测中发现的两个问题

### 3.1 CLI `--build` 在新表结构下已不可用（M1 必修）

```
psycopg.errors.NotNullViolation: null value in column "document_id" of relation "rag_chunks"
DETAIL: Failing row contains (1, probe.txt, null, 0, ...)
```

原因：03 §6.3 的迁移把 `rag_chunks.document_id` 收紧为 `NOT NULL`，而 `server/chunk_repository.insert_chunks()` 仍按旧列写入、`document_service` 也还不存在（没有先建 `documents` 行）。

- **影响**：现有 CLI 的 `--build` 完全不可用（不是性能问题，是结构不匹配）；`--ask`/预览仍可用。
- **修复**：M1 的仓储层必须提供"先 `INSERT documents` 拿 `id` → 再批量写 chunks（带 `document_id`）"，并在同一事务内更新 `chunk_count`。这本来就是 M1 的内容，但现在有了实测证据，优先级从"计划"变成"已知阻塞"。
- **副作用确认**：失败的事务已回滚，库内 `rag_chunks` 仍为 0 行（实测）。

### 3.2 冷启动时间被低估了 2~7 倍

02 §1.4 写"冷启动仍需约 10 s"，实测 **21.6 s（热盘）/ 70.8 s（冷盘）**。

- **影响**：G2 的"模型加载中"提示可能要持续 20~70 s；用户第一次提问的等待会被感知为"卡住"；健康检查在加载期间必须稳定返回 `embedding_model="loading"`。
- **不改变架构**：S-01 单 worker + 启动后台加载仍然成立；但前端提示文案与健康检查轮询（30 s，06 A3）需要按 20 s+ 设计，不能假设 10 s 就绪。
- **可选优化**（不在本期范围）：换 ONNX Runtime 或量化模型可显著降低加载与推理时间，但那会改技术栈，需单独立项。

## 5. 复测方法（可重复执行）

```bash
# 1) 嵌入吞吐（合成 50 页文本量）
python - <<'PY'
import time, os
os.environ.setdefault("HF_HOME", r"D:\models\huggingface")
from server import splitter, embedder
para = "本节介绍知识库问答系统的整体流程。用户上传文档后，系统依次完成解析、切分、向量化与入库。"
text = (para * 40 + "\n") * 50
chunks = splitter.split_documents([{"text": text, "source": "synthetic-50p.txt", "page": None}])
embedder.embed_documents(["预热"])
t0 = time.perf_counter(); embedder.embed_documents([c["text"] for c in chunks])
print(len(chunks), "块", f"{time.perf_counter()-t0:.1f} s")
PY

# 2) 冷启动（新进程，磁盘缓存热/冷各测一次）
python -X importtime -c "import torch" 2>&1 | tail -1
```
