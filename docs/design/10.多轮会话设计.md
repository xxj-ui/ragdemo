# 10. 多轮会话设计（草案）

> **定位**：把"一个会话里可以连续多轮提问、且上下文有承接"落成可实施的设计。当前系统是"一问一会话"，本文说明它为什么被锁死、要改成什么样、改哪几层、代价多少。

## 1. 现状：为什么现在"一问一会话"

不是遗漏，是**三处设计互相锁死**，其中一处是数据库硬约束。

| 层 | 现状 | 证据 |
| --- | --- | --- |
| 数据库 | `uq_messages_conversation_role UNIQUE (conversation_id, role)`，同一会话每种角色只能有一条 | `scripts/sql/schema.sql` 第 4 张表；注释里仍留着 `[待确认 Q2] 若裁决不锁定单轮，删除本约束…` |
| 服务层 | `chat.ask_stream()` 不接收会话 id；`_save()` 每次 `create_with_messages()` 新建会话 + 2 条消息 | `server/services/chat.py:75`、`server/db/conversations.py` 头部注释："每问一次 = 新建一个会话" |
| 契约 / 前端 | `POST /api/chat` 只收 `{question}`；`done` 返回的 `conversation_id` 未用于下一问；点历史会话置 `replaying=true` 只读 | `server/api/schemas.py` `ChatRequest`、`web/src/state/chatStore.ts:123` |

两个附带问题：

1. `conversations` 表**只有 `created_at`**，列表按创建时间倒序 → 即使支持多轮，老会话也不会因为新消息浮到顶部。
2. SRS §1.2「本期不包含」原写着 **"多轮对话上下文与查询改写"**——本次已通过 SRS v0.12 变更范围：多轮上下文转入「本期包含」，**查询改写仍保留在「本期不包含」**。

## 2. 已定口径（2026-11-03 裁决）

| # | 决策 | 结论 | 理由 |
| --- | --- | --- | --- |
| 1 | 档位 | **L1 + 确定性 query 拼接**：历史进提示词；检索 query = 上一轮 user 问题 + 当前问题（2026-11-04 修订；原 L2 的模型改写降为"后续可选、本轮不实施"，见 §7） | 确定性拼接零额外模型调用、延迟与评测都可预测；L2 改写要多一跳（+0.5~1.2 s），且没有评测集就无法证明改写真比拼接好 |
| 2 | 上下文窗口 | **最近 5 轮（10 条消息）+ 4000 字预算**，超了从旧到新丢 | 比 3 轮更完整，token 成本约翻倍，可接受 |
| 3 | 历史会话 | **点开后可直接继续提问**（取消 `replaying` 只读语义） | 回放→续聊更符合会话直觉 |
| 4 | 排序 | `conversations` 加 **`updated_at`**，列表按最近活动倒序 | 否则多轮会话永远沉在下面 |

## 3. 目标语义

**一个会话 = 有序的 Q/A 轮次序列**；每轮的 `citations` 独立归属该轮的 assistant 消息；标题取首问，后续轮次不重命名。

明确不做：

- 会话重命名 / 手动置顶
- 历史摘要压缩（L3，等长会话真实使用后再议）
- 跨会话记忆、用户画像
- 多轮评测指标（CRUD-RAG 全是单轮样本，评测必须走"不传 `conversation_id`"这条老路径）

## 4. 数据模型与迁移

### 4.1 结论

**不改表结构，只做三件事**：删单轮约束、补索引、给 `conversations` 加 `updated_at`。

| 对象 | 现状 | 目标 |
| --- | --- | --- |
| `messages` 唯一约束 | `(conversation_id, role)` | **删除** |
| `messages` 索引 | 无（靠唯一约束的隐式索引） | `(conversation_id, id)` |
| `conversations.updated_at` | 无 | `timestamptz NOT NULL DEFAULT now()` |
| `conversations` 索引 | `(created_at DESC, id DESC)` | 新增 `(updated_at DESC, id DESC)`；旧索引保留（历史列表仍可能按创建时间查） |
| `messages.citations` | `jsonb` 数组，已支持多条 | 不变，每条 assistant 消息各存自己的本轮引用 |

### 4.2 迁移方式：yoyo-migrations（版本化）

**工具裁决（2026-11-04）**：DDL 改由 [yoyo-migrations](https://pypi.org/project/yoyo-migrations/) 管理，不再手写一次性 SQL 人肉执行。理由：纯 SQL 文件、单个 pip 包、原生支持 `postgresql+psycopg://`（项目正是 psycopg 3），自带版本表与校验和。迁移总规则见 [03 数据库设计](03.数据库设计.md) §6.7。

目录与命名：

```
scripts/sql/migrations/
  V001__init_schema.sql                      # 基线：现有 4 张表（由 schema.sql 搬入）
  V002__multiturn_conversations.sql          # 本设计新增
  V002__multiturn_conversations.rollback.sql # 对应回滚（yoyo 约定：同名 + .rollback.sql）
```

`scripts/sql/migrations/V002__multiturn_conversations.sql`：

```sql
-- v002: 多轮会话（删单轮唯一约束、补索引、给会话加 updated_at）
-- depends: V001__init_schema
-- 说明：yoyo 把每个迁移放在单个事务里执行，文件内不写 BEGIN/COMMIT。

ALTER TABLE messages DROP CONSTRAINT IF EXISTS uq_messages_conversation_role;

CREATE INDEX IF NOT EXISTS idx_messages_conversation_id
    ON messages (conversation_id, id);

ALTER TABLE conversations ADD COLUMN IF NOT EXISTS updated_at timestamptz;
UPDATE conversations SET updated_at = created_at WHERE updated_at IS NULL;
ALTER TABLE conversations ALTER COLUMN updated_at SET NOT NULL;
ALTER TABLE conversations ALTER COLUMN updated_at SET DEFAULT now();

CREATE INDEX IF NOT EXISTS idx_conversations_updated_at
    ON conversations (updated_at DESC, id DESC);

-- 回填：现有单轮会话的 updated_at 取最后一条消息时间
UPDATE conversations c
   SET updated_at = m.last_at
  FROM (SELECT conversation_id, max(created_at) AS last_at
          FROM messages GROUP BY conversation_id) m
 WHERE m.conversation_id = c.id AND m.last_at > c.updated_at;

-- 回滚不写在注释里：yoyo 约定放在同名文件 V002__multiturn_conversations.rollback.sql，
-- 内容为下面四行（`yoyo rollback` 才会执行到它）：
--   ALTER TABLE messages ADD CONSTRAINT uq_messages_conversation_role UNIQUE (conversation_id, role);
--   DROP INDEX IF EXISTS idx_messages_conversation_id;
--   DROP INDEX IF EXISTS idx_conversations_updated_at;
--   ALTER TABLE conversations DROP COLUMN IF EXISTS updated_at;
```

### 4.3 存量库的基线与执行

- **不能**对现有库 `yoyo apply V001`：库里已有 4 张表、1 份文档（4,576 片段）与若干会话，V001 会重复建表；
- 正确做法：`yoyo mark V001__init_schema` 只写入一行版本记录（不动任何数据），之后 `yoyo apply` 只跑 V002；
- 执行入口封装在 `scripts/`（读 `RAG_DB_DSN`），**手动执行**；应用启动只做版本校验并日志告警，不隐式改库；
- 已执行的迁移文件**禁止修改**（校验和不符会报错），修正只能追加 `V003__fix_xxx.sql`。

### 4.4 `schema.sql` 的定位（降级为快照）

- `schema.sql` 不再作为迁移手段，只保留为**全量快照**：新环境对照 / 人工重建时参考；
- 内容与 `V001__init_schema` 一致；后续结构变更只进 `migrations/`，**不回写 `schema.sql`**（否则又是两套真相）；
- "新库一键建库"改为 `yoyo apply`（V001→V002 顺序执行），不再 `psql -f schema.sql`。

### 4.5 历史数据兼容

现有会话都是单轮（1 条 user + 1 条 assistant），删约束后天然满足新模型：`updated_at` 回填后排序正确，`get_with_messages` 改按 `id` 排序即可正确读出多条。

## 5. 会话生命周期

```
用户提问（conversation_id = null）
   └─ 建会话（title = 首问前 30 字）
      └─ 检索 → 生成 → 事务内写 user + assistant → done{conversation_id}
用户在同一会话继续提问（conversation_id = N）
   ├─ 校验会话存在（否则 404 CONVERSATION_NOT_FOUND）
   ├─ 取锁（会话级串行）
   ├─ 取最近 5 轮 / 4000 字历史（§6）
   ├─ 查询改写（§7）→ 用改写后的 query 检索
   ├─ 生成（system + 历史 + 本轮资料）
   ├─ 事务内 append user + assistant，并 bump updated_at
   └─ done{conversation_id = N}
失败路径（沿用现状，2026-11-04 裁决）
  首轮失败 → 会话未创建，整轮不写库，error 事件不带 conversation_id
  后续轮失败 → 本轮两条消息都不写，updated_at 不变；error 事件带当前 conversation_id，可继续提问
  客户端断开 → 停止生成，整轮不写库（SRS 7.4）
```

## 6. 上下文组装

### 6.1 参数（进 `server/core/config.py`）

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `history_max_turns` | 5 | 最多带最近 5 轮 |
| `history_char_budget` | 4000 | user + assistant 文本合计字符上限 |
| `rewrite_enabled` | **false** | 查询改写总开关；本轮不实施，参数预留给后续 |
| `rewrite_timeout` | 5.0 s | 改写调用超时，超时回退原问题 |
| `rewrite_max_tokens` | 64 | 改写输出上限（只输出一个问句） |

### 6.2 取数规则

1. 按 `id` 倒序取最近 N 条消息，拼成 (user, assistant) 对；
2. 从**新到旧**累加字符数，超过 4000 字即停止（保证最近的内容一定在）；
3. 再**反转为旧→新**顺序进入提示词；
4. 落库永远存全文，截断只发生在"送进模型"这一步。

### 6.3 提示词结构

```
system: 既有 SYSTEM_PROMPT（按知识库作答、标引用编号、找不到就说找不到）
user/assistant: 历史轮次原样交替（只放文本，不含引用卡片）
user: 参考资料：
      [1] 文件名，第 N 页
      正文…
      …
      问题：{本轮问题}
```

### 6.4 为什么历史里不放 citations

历史引用是 JSON 卡片结构（文件名 / 页码 / 摘要），塞进提示词只会：① 吃掉 token；② 让模型误把"上次的引用编号"当成本轮可用的编号，导致 `[n]` 与实际 citations 错位。**引用编号只在当轮有效**。

## 7. 查询改写（**本轮不实施，仅作后续可选设计**）

> **状态（2026-11-04 裁决）**：检索 query 改用 **确定性拼接**（上一轮 user 问题 + 当前问题），本节描述的模型改写**不在本轮实现范围**，参数 `rewrite_enabled` 默认 `false`。保留本节的目的是把"以后要不要上改写"的判断依据与代价留在案上，不是待办。

### 7.1 触发条件

- `rewrite_enabled = true` 且存在历史（首轮不调用，省一次延迟）；
- 本轮问题长度 ≥ 4 字（极短输入交给模型判断也无意义）。

### 7.2 提示词草案

```
system: 你是查询改写器。把用户的追问结合对话历史改写成一条可独立检索的问题。
        只输出改写后的问题本身，不要解释、不要引号、不要编号。
user: 历史：
      用户：… / 助手：…
      追问：{question}
```

- `temperature = 0`，`max_tokens = 64`，模型沿用 `deepseek-chat`。

### 7.3 失败回退

超时、网络错误、返回空、返回长度 > 200 字 → **一律回退原问题**，并在日志里记 `rewrite=failed/fallback`，主链路不受影响。

### 7.4 成本与延迟

| 项 | 影响 |
| --- | --- |
| 延迟 | 首字节 +0.5 ~ 1.2 s（多一次模型往返） |
| 费用 | 每轮多一次小调用（输入 ≤ 4k 字、输出 ≤ 64 token） |
| 可观测 | 日志字段：`rewritten=true/false`、`rewrite_ms`、`query_used`（脱敏后） |

### 7.5 不展示给用户

改写结果只用于检索，**不进界面**（否则用户会看到"两个问题"而困惑）；需要排查时看日志。

---

## 8. 检索与引用语义

- 检索用**改写后的 query**；引用编号仍按本轮检索结果的顺序从 1 开始；
- 每轮 `citations` 独立写入该轮 assistant 消息的 `messages.citations`；
- 答案里的 `[n]` 只对应当轮 citations（前端"引用来源"的收敛逻辑已按此实现）；
- 历史轮次的引用不会因新一轮检索而改变。

---

## 9. 并发与一致性

| 场景 | 处理 |
| --- | --- |
| 同一会话并发两问 | `Container` 内按 `conversation_id` 取 `asyncio.Lock`，串行化（单 worker 前提下够用）。**已实现**：`Container.conversation_lock()`；`ask_stream` 把流程拆成 `_run_turn`，续聊时持锁 |
| 一问一答写入 | 同一事务内写两条消息 + `UPDATE conversations SET updated_at = now()`，避免"半轮" |
| 生成失败 / 客户端断开 | 不写库（沿用现有语义），`updated_at` 不变 |
| 会话被删除后再提问 | 校验不到 → 404 `CONVERSATION_NOT_FOUND`，前端提示"会话已删除" |
| 锁表清理 | 会话数量级小（本机单用户），先不做回收；后续若需要可加 LRU |

## 10. 契约变更

### 10.1 `POST /api/chat` 请求体

```json
{ "question": "那它对谁影响最大？", "conversation_id": 12 }
```

- `conversation_id` 可选；**不传 = 新建会话**（与当前行为完全一致，评测脚本走这条路径）。

### 10.2 `done` 事件

保持不变：`{"conversation_id": N}`。前端用它维持当前会话。

### 10.3 新增错误码

`CONVERSATION_NOT_FOUND`（404，"会话不存在或已删除"）。

### 10.4 API-5 历史列表

响应项增加 `updated_at`，排序改为 `updated_at DESC, id DESC`（前端据此显示"最近活动"）。

### 10.5 兼容性

- 老客户端不传 `conversation_id` → 行为不变；
- 8 个既有接口的**路径与方法不变**，属于同一接口的语义扩展。

## 13. 验收标准（可执行，实测而非推断）

| # | 场景 | 期望 |
| --- | --- | --- |
| 1 | 同一会话连问 3 轮 | `messages` 6 行、`conversations` 1 行、`updated_at` 递增、侧边栏浮顶 |
| 2 | 指代追问（"这篇报道是谁写的""那它对谁影响最大"） | 检索命中且引用对得上**当前轮** |
| 3 | 不传 `conversation_id` | 行为与改造前完全一致（评测基线不受影响） |
| 4 | 同一会话并发两问 | 不交错、无"半轮"、两次都落库 |
| 5 | 某轮生成失败（LLM 超时） | 整轮不写库、返回 `error`；已有会话仍可继续提问，首轮失败则不留会话 |
| 6 | 历史超 5 轮 / 4000 字 | 只带最近部分，回答不报错，落库仍存全文 |
| 7 | 点历史会话继续问 | 追加到同一会话，不新建 |
| 8 | 会话被删除后继续问 | 404 `CONVERSATION_NOT_FOUND`，前端友好提示 |

## 14. 成本与风险

**工作量**：≈ 1.5 人天（含 4 份文档同步），不含评测。

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| 检索与生成不同源 | 历史给了模型、检索却用原问题 → 追问召回为空 | query 用"上一轮问题 + 当前问题"，把指代所需的上下文补进检索 |
| 首字节变慢 | 历史进 prompt（5 轮约 +3~4k 字符） | 4000 字预算封顶；实测若首字节 >2.5 s，把 `history_max_turns` 降到 3 |
| 评测污染 | 多轮上下文会让 CRUD-RAG 单轮指标失真 | 评测脚本固定"不传 `conversation_id`"；`rewrite_enabled` 可关 |
| 迁移不可逆 | 删除唯一约束后无法"回到单轮" | 约束本身只是完整性防线；若需回滚，可用 `scripts/sql/schema.sql` 重建约束（要求无多轮数据） |
| token 成本上升 | 5 轮历史约 3~4k 输入 token/次 | 4000 字预算封顶；后续可加摘要压缩（L3） |
| 提示词漂移 | 历史进提示词后，模型可能更"顺着用户说"而非依资料 | 保留"找不到就说找不到"约束；用现有 `questanswer` 样本做回归对比 |
